# Phase 4a live check: specification and acceptance criteria

Written 2026-10-23, about 21:05 IST, **before** the check was run. Script: `scripts/live_check_phase4a.py`. Results:
`docs/results/live_check_phase4a.md` and `results/live-checks/phase4a.json`. Criteria are not changed after the run; a
failed criterion is reported as failed.

## What is checked
The commits since `demo-stable-1` that change live behaviour:
- `18a4b38`: an anomaly seen only by the joint forest score ("unusual combination") never runs automatically;
- `d1c710d` + `65dd9fe`: two close root candidates -> abstain, with margin 0.1215 from out-of-fold training incidents;
- `84a3094`: SQLite learn store and `POST /feedback`;
- `d084b20`: forecast on every tick. This one is checked separately by the forecast check v3.

## Set-up
- Real Docker Compose stack, telemetry condition T3 (as `scripts/demo.ps1`).
- Brain image built from the checked-out commit, recorded in the results.
- Rulebook `eternalai/rulebooks/default.yaml`, mode autopilot.
- A throwaway approval token and chaos token generated by the script and passed only through the environment.
- The Docker lock is taken (`scripts/stack_lock.py`).
- The run waits until at least 1.8 GB of RAM is free.

## Evaluator runs
1. `crash` on `web`: expected low-risk restart by autopilot.
2. `crash` on `payments`: protected; the proposal waits; the script **rejects** it.
3. `error_spike` on `orders`: restart is medium risk under the default rulebook, so it waits; the script **approves** it.

## Acceptance criteria (each PASS / FAIL)

| id | criterion |
|---|---|
| A1 | `/status` shows `root_margin` = 0.121529 (the committed artifact), `learn_store.error` empty, rulebook `default.yaml`, mode autopilot |
| A2 | Every diagnosed incident from the three runs records `diagnosis.anomaly_source` (one of `down`, `limits`, `forest_only`, `none`), `diagnosis.root_gap` and `diagnosis.root_margin` = 0.121529 |
| A3 | Consistency, over every diagnosed incident of the three runs: (i) every incident with `root_gap < root_margin` abstained (for this or an earlier reason, e.g. the novelty gate); (ii) every abstention with the reason "two close root candidates" has `root_gap < root_margin`; (iii) every incident with `anomaly_source == forest_only` has no automatically executed action. (Refined before any run: an incident that already abstained for another reason keeps that reason.) |
| A4 | Run 1 (crash on web): a `restart_service` on `web` executed by `autopilot` |
| A5 | Run 2 (crash on payments): a proposal for `payments` waits with reason "protected"; after reject the incident is escalated; no action executed on `payments` |
| A6 | Run 3 (error_spike on orders): the proposal waits (medium risk) and nothing runs before approval; after approval it is executed by `human:live-check` |
| B1 | Every incident from the three runs that is closed by the end of the check is in the learn store (`GET /learn/{id}`) with the same `status` and the same action verdicts as `GET /incidents/{id}`; diagnosed ones have non-empty `root_features`; incidents with an executed action have an outcome row |
| B2 | `POST /feedback/{id}`: refused without a token (403); 404 for an id that is not stored; 200 with the token for a stored incident; `GET /learn/{id}` then shows that feedback |

## How each item is labelled in the report
- **Live verified:** the behaviour happened in this run and the criterion passed.
- **Active and consistent live, not triggered:** for "forest-only -> approval" and "close candidates -> abstain" when no
  real incident in the run had that condition. A3 still checks that no incident contradicts the rule. The behaviour
  itself then remains **unit-tested only**.
- **Standing limit:** none of this shows safety on unseen faults (`docs/postmortems/cpu_burn_seed426.md`; the margin
  would not have caught that case).
