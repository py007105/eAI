# Data

Every number below comes from a script in this repo; the file that holds it is named next to it.
Rerun the scripts to reproduce. Raw inputs and downloads are git-ignored (see `.gitignore`).

## 1. Sources and what each is used for

| Source | Size / content | Used for | Not used for |
|---|---|---|---|
| Training workbook (`EternalAI_training_dataset_v1.xlsx`, supplied by the project owner) | 295 labelled cases, 7,880 service rows, 4 systems, 17 sheets | root-cause ranker experiments, runbook retrieval text, label mapping, data-quality findings | cross-system fault classification (see 2) |
| RCAEval RE1 (Zenodo 14590730, MIT) | 375 cases: Online Boutique, Sock Shop, Train Ticket; faults cpu/mem/disk/delay/loss; metrics only; 372 MB downloaded | cross-system evidence (leave-one-system-out), public-data results table | disk fill, crash, bad deploy (it has none) |
| Live runs from this repo's own stack | produced by the independent evaluator (training seeds ≥ 1000) | detector, classifier, ranker training and the held-out evaluation | nothing else; see section 5 |

RCAEval caveats that matter: its `mem` fault is memory *stress* (a "close", not exact, match to a leak) and
its `disk` fault is disk *I/O* stress, not a full disk, so it does not fill the disk-fill gap
(`data/processed/rcaeval_index.csv`, column `mapping_quality`). RE2 (about 4.2 GB) and RE3 were not downloaded.

## 2. The training workbook: what is wrong with it

Full figures: `docs/DATA_QUALITY.md` (generated by `data/clean_workbook.py`).

- 295 cases, 7,880 rows: rows within a case are not independent, so every split is by whole case/run.
- `disk_io_ratio` and `socket_ratio` are 100% empty (dropped). Disk fields are missing in 7,821 of 7,880 rows (99.3%) and stay missing.
- 234 of 295 cases qualify as training truth (exact/close mapping, in scope). 61 are excluded: 43 approximate mappings, 18 out of scope (`logic_bug`, kept as the unseen-fault test).
- 8 of 12 labels exist in exactly one source (bad_deploy, crash, db_slowdown, disk_filling, logic_bug, memory_leak, network_delay, overload), so a model can learn "which dataset" instead of "which fault".
- The workbook's own `eternalai_demo` system has no latency or error features at all (100% missing), so models trained on the other systems cannot be scored on it with those features.
- All 17 knowledge-base rows are `reviewed_by_team = no`, and all 267 real-incident matches are keyword matches that nobody has verified. They are used only as clearly-labelled, unreviewed retrieval text, never as training truth.
- Several feature columns (`err_base`, `err_fault`, `err_delta`, `n_fault_points`) are defined against the known injection window, which a live system does not have. They are not used as live features; the live feature set is the rolling-window code in `eternalai/features/window.py`.
- The 59 recovery-outcome runs (3 to 5 per fault/fix pair, from the old prototype running as local processes) are far too few for RL or "optimal action" claims, and are not used to choose actions.

## 3. RE1 results and the system-identification finding

Source: `docs/results/rcaeval_re1.md` (`python data/build_rcaeval_features.py && python models/eval_rcaeval.py`).
Task: label the fault in the window at the root-cause service versus healthy windows of the same service;
300 incidents (disk-I/O faults excluded), 5 classes, 9 ratio/z-score features.

| Evaluation | logistic regression | shallow boosted trees | majority class |
|---|---|---|---|
| grouped 5-fold CV by incident, systems mixed (macro-F1) | 0.647 ± 0.044 | 0.774 ± 0.032 | 0.160 |
| leave-one-system-out, mean of 3 systems | 0.522 | **0.616** | 0.160 |
| train-fold macro-F1 (boosted trees) | | 0.935 | |

- Mixed-system CV flatters the model: 0.774 versus 0.616 once a whole system is held out.
- The boosted trees fit the training folds at 0.935 and test at 0.774 (a gap of +0.161), i.e. a variance problem; logistic regression has a small gap (+0.028) but lower accuracy, i.e. higher bias.
- Learning curve: test macro-F1 stops improving at about 0.78 from 60% of the training incidents onward, so more data of the same kind is unlikely to help; the limit is the features' cross-system validity.
- **System identifiability:** a boosted-tree probe predicts *which system* a row came from with macro-F1 **0.892** (chance about 0.33) using the very same features. The classifier can therefore shortcut on system identity, which is the likely reason cross-system transfer is weak.
- Shuffled-label control (labels permuted per incident): macro-F1 0.278, close to chance, so there is no direct leakage from incident identity.

## 4. Attempts to improve transfer

See `docs/results/transfer_re1.md` (`python models/eval_transfer.py`), which tests per-system normalisation, dropping system-identifying features (chosen on the training systems only), and their combination, with bootstrap confidence intervals resampled by incident (500 resamples).

Result: **nothing beat the current model (leave-one-system-out macro-F1 0.616, 95% CI [0.586, 0.644]).** The best variant, per-system normalisation plus dropping identifying features, scored 0.630 with a difference-to-current interval of [-0.023, +0.049], which includes zero. The current model is kept. Dropping identifying features did lower the system-identification probe (0.896 on all 11 candidate features to about 0.70 on a 3-feature subset), but the systems stay clearly distinguishable (chance is 0.33) and fault F1 did not improve. Logistic regression was worse than boosted trees in every setting (about 0.51 versus 0.61), with intervals that do not overlap.

## 5. Live-generated data (this repo's stack)

Produced by `models/collect_runs.py` through the evaluator: faults crash, latency, error spike, memory leak, disk fill, bad deploy, cpu burn (unseen), plus healthy traffic surges and good deploys as negatives. Run order is shuffled per repetition, and the evaluator waits long enough after any release change that one run cannot show up as "recent deploy" in the next.

Full output: `docs/results/runs_sanity.md` (`python models/check_runs.py`), run before any model was trained.

- **Complete:** 72 of 72 planned runs (9 scenarios x 8 repetitions, training seeds 1000-1707). The first pass saved 63; the other 9 failed and were re-run.
- **Why 9 runs failed first time:** a race in the evaluator. It reported a run as finished before the restore that follows had completed, so the collector started the next run while containers were still being recreated ("expected 1 container, found 0"). Fixed (`evaluator/main.py`, regression test `tests/test_evaluator_state.py`); the 9 seeds were then re-run one at a time.
- **Excluded as corrupted: 4 of 72**, each with its reason in `data/runs/EXCLUDED.json`: `cpu_burn_1406` (the target's CPU series is missing after injection), `good_deploy_1008` and `good_deploy_1508` (38-42% of pre-injection request rates missing: scrape gaps), `latency_1501` (53% missing, same cause). 68 runs remain: crash 8, latency 7, error spike 8, memory leak 8, disk fill 8, bad deploy 8, cpu burn 7, traffic surge 8, good deploy 6.
- **A threshold I changed after seeing results:** the first version of the check required 15 post-injection samples and flagged 21 runs, 17 of them only for having 12-14 samples. The default 45 s run saves about 34 s (13 samples) of post-injection data by design, so the threshold was stricter than the collection plan and I lowered it to 10. The faults in those 17 runs were clearly visible in the signals (for example bad deploys at about 70% error ratio).
- **Every injected fault is visible** in the target service's signals in the 68 retained runs (a per-run check: crash = not scraped, latency = p95 jump, errors, memory growth or death, disk growth, deploy signal plus errors, CPU rise, traffic rise).
- **No leakage found:** no raw signal column or model feature name contains a scenario name, injection flag or ground-truth field, and none of the evaluator-only fields are columns of the run files. `deploys_3m` and `restarts_in_window` come from `app_release_seq` and `app_start_time_seconds`, which a production monitor can see.
- **Run order does not predict the label:** Kruskal-Wallis of run position across scenarios p = 0.98; AUC of predicting fault-versus-healthy from run position alone 0.448 (0.5 = nothing); previous scenario versus current scenario chi-square p = 0.26.
- **One drift flag:** the `orders` memory baseline falls with run position (Spearman rho -0.36, p = 0.003), probably because early runs used a long-running container with a grown database and later ones used freshly recreated containers. It is carried into model training as a known risk and tested with an ablation in `docs/results/models_cv.md` rather than assumed harmless.

Limits that apply to all live data: one application (four Python services), faults injected by a script on one machine, a single workload generator, and no-action runs only (EternalAI was not running while collecting).
