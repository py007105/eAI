## Components

- **Detector** (per service): IsolationForest on 10 traffic-normalised features, threshold = largest healthy validation score + slack, plus learned healthy-range limits per feature. Features: ['lat_ratio', 'cpu_per_req_ratio', 'error_ratio', 'dep_fail_rate', 'error_log_rate', 'mem_rel_growth', 'mem_slope_share_per_min', 'scratch_mb', 'scratch_slope_mb_per_min', 'up_frac'].
  - forest thresholds per service: web=0.843, orders=0.711, inventory=0.712, payments=0.657
  - learned limits (web): cpu_per_req_ratio: [0.362, 2.12], dep_fail_rate: [-0.025, 0.5], error_log_rate: [-0.00887, 0.453], error_ratio: [-0.00402, 0.0842], lat_ratio: [-0.351, 2.82], mem_rel_growth: [-0.642, 0.029], mem_slope_share_per_min: [-0.0341, 0.0528], scratch_mb: [-2e-11, 2e-11], scratch_slope_mb_per_min: [-2e-11, 2e-11]
- **Classifier**: gradient boosting (NaN-aware) with temperature scaling (T = 0.95); classes ['bad_deploy', 'disk_fill', 'down', 'error_spike', 'healthy', 'latency_spike', 'memory_leak']; confidence abstain threshold 0.40; 40 features (including observed-masks).
- **Novelty gate**: mean distance to the 5 nearest known windows over 12 features; abstain above 1.117 (the 99% quantile of out-of-fold distances).
- **Root-cause ranker**: gradient boosting over 10 evidence features: ['anomaly_score', 'anomalous', 'earliness', 'caller_blame', 'n_anomalous_callees', 'n_anomalous_callers', 'unavailable', 'recent_deploy', 'err_ratio', 'lat_ratio'].
- **Baselines** (healthy medians and spreads per service) for ['web', 'orders', 'inventory', 'payments'].

## Calibration

- out-of-fold ECE 0.0026; ECE on windows predicted as a fault class 0.013; the dashboard shows the probability as a percentage: True (rule: overall ECE <= 0.05 and fault-prediction ECE <= 0.10 with at least 50 such windows).

## Intended use and limits

- Intended for the four-service demo application in this repository, with the fault types injected by `evaluator/`.
- Trained on one application, on a single machine, with scripted faults and a single workload generator. Do not read these numbers as production accuracy.
- The detector's forest adds nothing measurable over the learned limits (see `docs/results/detector_margin.md`).
- A fault the model has not seen should be answered with an abstention, but the gate can miss faults that resemble a known one (hold-one-fault-type-out numbers are in `docs/results/models_cv.md`).
- The `orders` and `web` baselines drift with container age (`docs/results/runs_sanity.md`); live baselines should be refitted from recent healthy history in a long-running deployment.

## Notes for this version

- These models are the retrained set (git tag `models-v2`). They changed together with the memory features, the approval-queue fix and the telemetry condition; no change in behaviour is attributable to any one of them (Amendment 6). The previous card is kept as `docs/MODEL_CARD_v1.md`.
- The training runs combine **two telemetry conditions**: the original runs were made with the trace exporter on (the collector state at that time was not recorded) and the fresh runs with it off. The condition is not a model input and cross-validation folds mix both, so cross-validation cannot separate its effect. HYPOTHESIS, not a finding: that the exporter explains the v1 benchmark's memory shift (`docs/postmortems/telemetry-conditions-by-batch.md`).
- The unseen fault (cpu_burn) is not in training. On held-out evaluation seeds the abstention gate fired in some runs and not in others, and in one v2 run it let a wrong-service action through (`docs/postmortems/cpu_burn_seed426.md`). The gate must not be described as reliable on unseen faults. The decision was not to change it before the freeze.
- Benchmark results for these models: `docs/results/benchmark_v2.md`; caveats: the canonical section of `docs/EVALUATION.md`.
